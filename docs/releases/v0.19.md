# Frontile v0.19

v0.19 is the cleanup release that v0.18 promised. It removes what v0.18
deprecated, so the library stops carrying two of everything: one component
package instead of ten, and one name for each component argument.

It adds no new components. If your app runs on the latest 0.18.x with no
Frontile deprecation warnings in the console, there is very little left to do.

## Before you upgrade

**Get to zero deprecation warnings on 0.18.x first.** Almost everything v0.19
removes logged a deprecation warning in 0.18.x, and each warning names its
replacement. Upgrade to the latest 0.18.x, run your app and your test suite,
and work through the warnings with the
[v0.18 migration guide](../migrations/v0.18/index.md). When the console is
clean, upgrade to v0.19.

Two removals never warned, so check for them by hand: imports of the
`FrontileStickyOptions` type (it was only marked `@deprecated`), and overlay
components rendered from `.hbs` templates (see [`.hbs` templates](#hbs-templates)).

A warning you skip on 0.18 does not turn into a warning on 0.19. It becomes a
failure, and some of those failures are silent in production (see
[What breaks, and how loudly](#what-breaks-and-how-loudly)).

## What was removed

### Packages

| Removed                                                                                                                                                     | Use instead                                                                                                      |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `@frontile/buttons`, `@frontile/collections`, `@frontile/forms`, `@frontile/notifications`, `@frontile/overlays`, `@frontile/status`, `@frontile/utilities` | `frontile`, or a category entry point such as `frontile/forms`. These packages only re-exported from `frontile`. |
| `@frontile/forms-legacy`                                                                                                                                    | `frontile` forms. See the [Forms Legacy migration guide](../migrations/v0.18/forms-legacy.md).                   |
| `@frontile/changeset-form`                                                                                                                                  | `frontile` forms. See the [Changeset Form migration guide](../migrations/v0.18/changeset-form.md).               |

`@frontile/theme` stays. It is a separate package, not a wrapper.

The last 0.18.x release of each removed package stays on npm. They are marked
deprecated there and get no further releases.

### Component arguments

The old names of the two styling axes are gone. `@appearance` became
`@variant`, and `@intent` became `@color`, or `@status` on `FormFeedback`.

| Component                                                        | Removed                                          | Use instead                                       |
| ---------------------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------- |
| Button, ButtonGroup, ToggleButton                                | `@appearance`, `@intent`                         | `@variant`, `@color`                              |
| Listbox (and its Item and Group), Dropdown, Select, Autocomplete | `@appearance`, `@intent`                         | `@variant`, `@color`                              |
| Chip                                                             | `@appearance`, `@intent`, `@radius`              | `@variant`, `@color`; `Badge` for a squared label |
| Select's `@chip` options                                         | `appearance`, `intent`, `radius`                 | `variant`, `color`                                |
| CloseButton                                                      | `@onClick`; `@variant="transparent"`, `"subtle"` | `@onPress`; `"ghost"`, `"soft"`                   |
| Spinner, ProgressBar, Switch                                     | `@intent`                                        | `@color`                                          |
| FormFeedback                                                     | `@intent`                                        | `@status`                                         |

The values were renamed along with the arguments. `default` became `neutral`
on every color axis, and the variant values differ per component (Chip's
`faded` is `soft`, Listbox's `faded` is `subtle`). The
[Component API Naming guide](../migrations/v0.18/component-api-naming.md) has
the full mapping.

### Notifications

The `appearance` option is gone, along with the `NotificationAppearance` type.
Use `status`, with `danger` in place of `error` and `primary` in place of
`info`:

```js
this.notifications.add('Saved', { status: 'success' });
```

This applies to the options you pass to `add()` and to the
`'@frontile/notifications'` defaults in `config/environment.js`.

### Types and theme exports

- `FrontileStickyOptions` is gone. Use `FrontileColumnOptions`, which it was an
  alias of.
- `@frontile/theme` no longer exports the `forms-legacy` recipes (`formInput`,
  `formTextarea`, `formCheckbox`, `formRadio`, `formCheckboxGroup`,
  `formRadioGroup`, `formSelect`). The Tailwind plugin no longer styles
  `ember-power-select`, and the theme no longer depends on
  `tailwindcss-ember-power-select`. If your app still uses ember-power-select
  directly, style it in your own CSS.
- `Select` and `NativeSelect` no longer log a warning when you pass
  `@selectedKeys` in single-selection mode. The argument is still ignored
  there; use `@selectedKey`.

## What breaks, and how loudly

| If you still use                                               | What happens                                                                                                   | Fails how?                                   |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| An import from a removed `@frontile/*` package                 | The module cannot be resolved                                                                                  | Loudly, at build time                        |
| A removed argument, in a `.gts`/`.gjs` file checked by Glint   | A type error naming the unknown argument                                                                       | Loudly, at type-check time                   |
| A removed argument or option, in a development or test build   | A failed assertion that names the replacement, e.g. `Button: @appearance was removed in 0.19.0. Use @variant.` | Loudly, the first time the component renders |
| A removed argument or option, in a production build            | Ignored. The component renders with its default (see below)                                                    | **Silently**                                 |
| A `forms-legacy` recipe from `@frontile/theme`                 | The import does not exist                                                                                      | Loudly, at build or type-check time          |
| A Modal, Drawer, Popover or other overlay in a `.hbs` template | The component cannot be found (see [`.hbs` templates](#hbs-templates))                                         | Loudly                                       |

**The production row is the one to worry about.** Development assertions are
stripped from production builds, so an argument your tests never rendered
reaches production as a no-op. Most of the defaults it falls back to are
harmless, but two are not:

- **`<FormFeedback @intent="success">` renders as an error.** Without
  `@status`, FormFeedback uses its default, `danger`. The message gets error
  styling and is announced assertively to screen readers.
- **A notification created with `appearance:` renders as neutral.** The
  `status` it was meant to set is not applied, so a success or error toast
  looks like an ordinary one.

The other removed arguments fall back to the component's default variant or
color. A CloseButton given `transparent` or `subtle` renders as `ghost`.

Run your test suite against v0.19 in a development build before you ship it.
That turns every remaining use into a failed assertion.

## `.hbs` templates

In 0.18.x, `@frontile/overlays` made thirteen components resolvable by name from
classic `.hbs` templates: `Modal` and `Drawer` (with their `Body`, `Header` and
`Footer`), `Backdrop`, `Overlay`, `Popover`, `Portal` and `PortalTarget`. None
of the other wrapper packages did that. Removing `@frontile/overlays` removes
those names.

Two ways forward:

- **Move the template to `.gts` or `.gjs`** and import the component from
  `frontile`. This is the format Frontile's docs and types assume.
- **Re-export the component from your app**, one file per name, until you
  migrate:

  ```js
  // app/components/modal.js
  export { Modal as default } from 'frontile';
  ```

  Nested names live in nested files, so `<Modal::Body>` needs
  `app/components/modal/body.js` exporting `ModalBody`.

This one gave no warning on 0.18.x: a `.hbs` lookup reached the component
without going through the package's entry point, which is where its
deprecation warning lived. Search your `.hbs` templates for the names above.

No other Frontile component was ever resolvable from `.hbs` through these
packages, so nothing else changes for `.hbs` users.

## Upgrading from v0.17 or earlier

Upgrade to the latest 0.18.x first, follow the
[v0.18 migration guide](../migrations/v0.18/index.md), and then come back here.
Jumping straight to v0.19 skips the deprecation warnings that tell you what
to change.
